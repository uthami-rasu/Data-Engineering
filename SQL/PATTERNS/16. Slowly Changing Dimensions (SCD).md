# SQL Pattern 16: Slowly Changing Dimensions (SCD)

## 1. What Is a Slowly Changing Dimension?

A **Slowly Changing Dimension (SCD)** is a data-warehouse technique used to handle changes in dimension data while deciding how much historical information should be preserved.

Typical dimension tables:

- Customer
- Employee
- Product
- Supplier
- Location

For example, a customer changes their city:

```text id="9gh3oq"
Before:
Customer 101 → Chennai

Customer changes address

After:
Customer 101 → Bangalore
```

The important question is:

> Should we overwrite Chennai, or should we keep Chennai as historical information?

SCD defines the answer.

---

# 2. Why Is SCD Important?

Consider a sales system.

A customer was:

```text id="x2lp5t"
2024 → Chennai
2025 → Bangalore
```

Suppose the customer made:

```text id="4q6f8o"
Order 1 → 2024
Order 2 → 2025
```

When analyzing historical sales, you may need to know:

> Where was the customer when each order happened?

If you simply overwrite:

```text id="0m6m2s"
Customer 101 → Bangalore
```

you lose the previous Chennai information.

SCD techniques solve this problem.

---

# 3. Main SCD Types

The important types are:

| Type | Meaning |
|------|---------|
| SCD Type 0 | Never change |
| SCD Type 1 | Overwrite old value |
| SCD Type 2 | Keep complete history |
| SCD Type 3 | Keep limited history |

For Data Engineering interviews, **Type 1 and Type 2 are the most important**.

---

# 4. SCD Type 0 — Never Change

## Concept

The original value is considered permanent.

Example:

```text id="ihqf6d"
Customer birth date
```

If birth date is:

```text
1995-05-10
```

we don't update it when the source contains a conflicting value.

---

## Example

### Original

| customer_id | name | birth_date |
|------------:|------|------------|
| 101 | Arun | 1995-05-10 |

Source later sends:

| customer_id | name | birth_date |
|------------:|------|------------|
| 101 | Arun | 1996-05-10 |

The warehouse keeps:

| customer_id | name | birth_date |
|------------:|------|------------|
| 101 | Arun | 1995-05-10 |

---

## Use Cases

- Original registration date
- Birth date
- Original customer creation date

---

# 5. SCD Type 1 — Overwrite

## Concept

When the dimension changes, simply update the existing row.

### Before

| customer_id | name | city |
|------------:|------|------|
| 101 | Arun | Chennai |

Customer moves.

### Source

| customer_id | name | city |
|------------:|------|------|
| 101 | Arun | Bangalore |

### Final Warehouse

| customer_id | name | city |
|------------:|------|----------|
| 101 | Arun | Bangalore |

The old value `Chennai` is lost.

---

# 6. When Do We Use Type 1?

Use Type 1 when history isn't important.

Examples:

- Correcting a spelling mistake
- Correcting an email
- Fixing invalid data
- Updating current customer information

Example:

```text id="h4h4mt"
"Arun Kumar"
      ↓
"Arun Kumaran"
```

You usually don't need the old spelling as business history.

---

# 7. Type 1 SQL Pattern

For PostgreSQL, one common approach is:

```sql id="ve7l3n"
INSERT INTO customer_dim (
    customer_id,
    name,
    city
)
VALUES (
    101,
    'Arun',
    'Bangalore'
)
ON CONFLICT (customer_id)
DO UPDATE SET
    name = EXCLUDED.name,
    city = EXCLUDED.city;
```

The existing row is updated.

---

# 8. SCD Type 2 — Preserve Full History

This is the most important SCD type for Data Engineering.

Instead of updating the old row, we:

1. Expire the old record.
2. Insert a new record.
3. Keep both records.

---

# 9. Type 2 Example

Customer initially lives in Chennai.

### Version 1

| customer_id | name | city | start_date | end_date | is_current |
|------------:|------|------|------------|----------|-----------:|
| 101 | Arun | Chennai | 2024-01-01 | NULL | true |

Customer moves to Bangalore on March 1.

Instead of replacing Chennai, we do:

### Final Dimension

| customer_id | name | city | start_date | end_date | is_current |
|------------:|------|------|------------|----------|-----------:|
| 101 | Arun | Chennai | 2024-01-01 | 2024-02-29 | false |
| 101 | Arun | Bangalore | 2024-03-01 | NULL | true |

History is preserved.

---

# 10. Why Do We Need `start_date` and `end_date`?

They tell us when each version was valid.

For the Chennai row:

```text id="jv5xge"
Valid from:
2024-01-01

Valid until:
2024-02-29
```

For Bangalore:

```text id="nt2g0s"
Valid from:
2024-03-01

Valid until:
NULL
```

This allows historical queries.

---

# 11. Why Do We Need `is_current`?

It makes finding the latest version easy.

Example:

```sql id="0d6pzz"
WHERE is_current = true
```

returns the current customer record.

Without it, you would often need:

```sql id="0uzemf"
MAX(start_date)
```

or another ranking technique.

---

# 12. Type 2 Standard Table Structure

A common dimension table looks like:

```sql id="h4oq2a"
CREATE TABLE customer_dim (
    customer_sk BIGSERIAL PRIMARY KEY,

    customer_id INT NOT NULL,

    name VARCHAR(100),
    city VARCHAR(100),

    start_date DATE NOT NULL,
    end_date DATE,

    is_current BOOLEAN NOT NULL
);
```

Important distinction:

```text id="1ycy5a"
customer_id
=
Business / source identifier

customer_sk
=
Warehouse surrogate key
```

---

# 13. Why Surrogate Keys Matter in Type 2

Suppose:

```text id="w8m2jc"
Customer 101
Chennai
```

becomes:

```text id="y0oo0o"
Customer 101
Bangalore
```

The business key is still:

```text id="yp5cje"
customer_id = 101
```

But the warehouse needs two versions.

Therefore:

```text id="0ptwus"
customer_sk = 1001
customer_id = 101
city = Chennai

customer_sk = 1002
customer_id = 101
city = Bangalore
```

The surrogate key uniquely identifies each dimension version.

---

# 14. Type 2 Change Detection

Before creating a new version, we first need to determine whether something actually changed.

Example:

### Existing

| customer_id | city | email |
|------------:|------|-------|
| 101 | Chennai | a@test.com |

### New Source

| customer_id | city | email |
|------------:|------|-------|
| 101 | Bangalore | a@test.com |

Only `city` changed.

We can compare the columns.

---

# 15. Template: Detect Changes With `LAG()`

Suppose we have multiple versions in a staging table.

```sql id="hf7h3o"
SELECT
    customer_id,
    effective_date,
    city,

    LAG(city) OVER (
        PARTITION BY customer_id
        ORDER BY effective_date
    ) AS previous_city

FROM customer_staging;
```

Then:

```sql id="g8osv9"
CASE
    WHEN city IS DISTINCT FROM previous_city
        THEN 1
    ELSE 0
END
```

This identifies changes.

`IS DISTINCT FROM` is useful in PostgreSQL because it handles `NULL` values safely.

---

# 16. Type 2 Processing Logic

The standard idea is:

```text id="2h1dgs"
Source Record
     ↓
Does customer exist?
     ↓
No ─────────→ Insert new version
     |
    Yes
     ↓
Did tracked attributes change?
     ↓
No ─────────→ Do nothing
     |
    Yes
     ↓
Expire current version
     ↓
Insert new version
```

---

# 17. Example

Existing:

| customer_id | city | start_date | end_date | is_current |
|------------:|------|------------|----------|-----------:|
| 101 | Chennai | Jan 01 | NULL | true |

New source:

| customer_id | city |
|------------:|------|
| 101 | Bangalore |

City changed.

Therefore:

### Step 1 — Expire Existing Row

```text id="f0w5bn"
end_date = new_start_date - 1 day
is_current = false
```

Result:

| customer_id | city | start_date | end_date | is_current |
|------------:|------|------------|----------|-----------:|
| 101 | Chennai | Jan 01 | Feb 29 | false |

### Step 2 — Insert New Version

| customer_id | city | start_date | end_date | is_current |
|------------:|------|------------|----------|-----------:|
| 101 | Bangalore | Mar 01 | NULL | true |

---

# 18. Type 2 SQL Example

## Step 1 — Expire Current Row

```sql id="xv8f6u"
UPDATE customer_dim
SET
    end_date = DATE '2024-03-01' - INTERVAL '1 day',
    is_current = FALSE
WHERE customer_id = 101
  AND is_current = TRUE;
```

Then insert:

```sql id="sqj4mt"
INSERT INTO customer_dim (
    customer_id,
    name,
    city,
    start_date,
    end_date,
    is_current
)
VALUES (
    101,
    'Arun',
    'Bangalore',
    DATE '2024-03-01',
    NULL,
    TRUE
);
```

---

# 19. Better Production Approach

In production pipelines, don't hard-code one customer.

Typically:

```text id="1hd5q1"
Staging Table
      ↓
Compare with Current Dimension
      ↓
Identify New Rows
      ↓
Identify Changed Rows
      ↓
Expire Changed Rows
      ↓
Insert New Versions
```

This is commonly implemented using:

- `MERGE`
- `UPDATE + INSERT`
- Delta Lake `MERGE`
- Snowflake `MERGE`
- ETL/ELT orchestration

---

# 20. Type 3 — Keep Limited History

Type 3 doesn't keep unlimited versions.

Instead, it stores the current value and the previous value.

### Example

Current:

| customer_id | current_city | previous_city |
|------------:|--------------|---------------|
| 101 | Bangalore | Chennai |

If the customer later moves to Mumbai:

| customer_id | current_city | previous_city |
|------------:|--------------|---------------|
| 101 | Mumbai | Bangalore |

Chennai is no longer stored.

So:

```text id="m5q8qf"
Type 2 → Full history
Type 3 → Limited history
```

---

# 21. Type 1 vs Type 2 vs Type 3

| Type | Old Value | History |
|------|-----------|---------|
| Type 0 | Never changed | Permanent |
| Type 1 | Overwritten | None |
| Type 2 | New row created | Full |
| Type 3 | Stored in another column | Limited |

### Problem

A customer changes their address.

The business wants to know:

Which SCD type should be used?

### Answer

**SCD Type 2**

Because we need historical versions.

# 23. Historical Query With Type 2

Suppose:

```text id="zhz2qe"
Customer 101
Chennai: Jan-Feb
Bangalore: Mar-present
```

And an order occurred:

```text id="q90qqq"
Order Date = Feb 15
```

We want the dimension version valid on Feb 15.

Condition:

```sql id="6a6oxg"
order_date >= start_date
AND (
    order_date < end_date
    OR end_date IS NULL
)
```

For Type 2 tables, another common pattern is:

```sql id="0htz2j"
order_date >= start_date
AND order_date < COALESCE(end_date, DATE '9999-12-31')
```

This allows historical fact-to-dimension matching.

---

# 24. Important Date Convention

One clean approach is to use a half-open validity interval:

```text id="g01rcc"
[start_date, end_date)
```

Meaning:

```text id="ynhmt9"
start_date <= date < end_date
```

Example:

| city | start_date | end_date |
|------|------------|----------|
| Chennai | Jan 01 | Mar 01 |
| Bangalore | Mar 01 | NULL |

Then:

```text id="b6wfk4"
Feb 15 → Chennai
Mar 01 → Bangalore
```

This avoids many boundary problems.

---

# 25. `LAG()` in SCD

You already learned `LAG()` for change detection.

It can identify when a dimension attribute changes.

Example:

```sql id="wmz1z4"
SELECT
    customer_id,
    effective_date,
    city,

    LAG(city) OVER (
        PARTITION BY customer_id
        ORDER BY effective_date
    ) AS previous_city

FROM customer_history;
```

Then:

```sql id="jxu6ry"
CASE
    WHEN city IS DISTINCT FROM previous_city
        THEN 1
    ELSE 0
END AS city_changed
```

So:

```text id="rq4e0w"
LAG()
   ↓
Detect Change
   ↓
SCD Type 2 Logic
```

# 26. Multiple Tracked Columns

Suppose we track:

```text id="i9zjy7"
city
salary
department
status
```

We need to detect whether any tracked attribute changed.

In PostgreSQL:

```sql id="lsjtsc"
city IS DISTINCT FROM previous_city
OR salary IS DISTINCT FROM previous_salary
OR department IS DISTINCT FROM previous_department
OR status IS DISTINCT FROM previous_status
```

`IS DISTINCT FROM` is safer than `<>` when `NULL` values are possible.

---

# 27. Hash-Based Change Detection

In large ETL pipelines, comparing many columns individually can become cumbersome.

A common technique is to create a hash of tracked attributes.

Conceptually:

```text id="h7b3bz"
city + salary + department + status
                ↓
              HASH
```

Then compare:

```text id="iayk6i"
existing_hash
vs
incoming_hash
```

If the hash changes, the dimension changed.

For example:

```sql id="7v80t5"
MD5(
    CONCAT_WS(
        '|',
        city,
        salary,
        department,
        status
    )
)
```

The exact implementation depends on the warehouse.

---

# 28. SCD Type 2 With `MERGE`

Modern data platforms often support `MERGE`.

Conceptually:

```sql id="phg8j3"
MERGE INTO customer_dim AS target
USING customer_stage AS source
ON target.customer_id = source.customer_id
AND target.is_current = TRUE

WHEN MATCHED
AND target.city IS DISTINCT FROM source.city
THEN
    -- expire current record

WHEN NOT MATCHED
THEN
    -- insert new record
```

However, a true Type 2 implementation often requires both:

```text id="xwuxfc"
Expire existing row
+
Insert new version
```

so the exact `MERGE` design varies by platform.

# 32. Common Mistakes

## Mistake 1 — Overwriting Type 2 Rows

Wrong:

```sql id="r5ek3u"
UPDATE customer_dim
SET city = 'Bangalore'
WHERE customer_id = 101;
```

This destroys the Chennai history.

---

## Mistake 2 — Creating a New Row for Every Load

Suppose the customer hasn't changed.

You shouldn't create:

```text id="s2en7f"
Jan → Chennai
Feb → Chennai
Mar → Chennai
```

unless the business explicitly wants periodic snapshots.

Type 2 should create a new version **when tracked attributes change**.

---

## Mistake 3 — Forgetting to Expire the Previous Version

If a new Type 2 row is inserted but the old row remains:

```text id="zv1stj"
is_current = true
```

you could end up with multiple current records.

There should normally be exactly one current version per business key.

---

## Mistake 4 — Incorrect Date Boundaries

Be consistent about whether `end_date` is inclusive or exclusive.

A half-open interval is often easier:

```text id="2h70ou"
start_date <= date < end_date
```

# 36. Final Mental Model

Remember SCD this way:

```text id="mhrx50"
Type 1
"I only care about the current value."

Type 2
"I care about every historical version."

Type 3
"I care about the current value
and only a limited amount of history."
```

For Data Engineering interviews, focus especially on **SCD Type 2**.

The core idea is:

> **When a tracked dimension attribute changes, don't overwrite the old version. Expire the old row and insert a new version so the warehouse can reconstruct history.**
