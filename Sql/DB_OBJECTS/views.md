Perfect. You've understood the main difference.

> **Table** = You manage the data.
>
> **Materialized View** = PostgreSQL manages the data generated by a query (through `REFRESH MATERIALIZED VIEW`).

Now let's cover all three in a structured way.

---

# Table

## Definition

A **table** is a database object that stores data physically in rows and columns.

- Stores actual/business data.
- Supports INSERT, UPDATE, DELETE.
- Data remains even after restarting PostgreSQL.
- Considered the **source of truth**.

---

## Syntax

```sql
CREATE TABLE table_name (
    column1 datatype,
    column2 datatype,
    ...
);
```

---

## Example

```sql
CREATE TABLE employees (

    id INT PRIMARY KEY,
    name VARCHAR(100),
    department VARCHAR(50),
    salary NUMERIC(10,2)

);
```

Insert data

```sql
INSERT INTO employees
VALUES
(1,'John','IT',60000),
(2,'Alice','HR',50000),
(3,'Bob','IT',70000);
```

Retrieve

```sql
SELECT * FROM employees;
```

Output

| id  | name  | department | salary |
| --- | ----- | ---------- | ------ |
| 1   | John  | IT         | 60000  |
| 2   | Alice | HR         | 50000  |
| 3   | Bob   | IT         | 70000  |

---

# View

## Definition

A **View** is a **virtual table**.

It **does not store data**.

Instead, it stores only the SQL query.

Whenever you query the view, PostgreSQL executes the stored SELECT statement against the underlying tables.

---

## Syntax

```sql
CREATE VIEW view_name AS
SELECT ...
FROM ...
WHERE ...;
```

---

## Example

Create a view

```sql
CREATE VIEW it_employees AS

SELECT
    id,
    name,
    salary
FROM employees
WHERE department = 'IT';
```

Query the view

```sql
SELECT * FROM it_employees;
```

Result

| id  | name | salary |
| --- | ---- | ------ |
| 1   | John | 60000  |
| 3   | Bob  | 70000  |

---

Suppose we insert

```sql
INSERT INTO employees
VALUES
(4,'David','IT',80000);
```

Now run

```sql
SELECT * FROM it_employees;
```

Output

| id  | name  | salary |
| --- | ----- | ------ |
| 1   | John  | 60000  |
| 3   | Bob   | 70000  |
| 4   | David | 80000  |

Notice:

The view updated automatically because PostgreSQL executed the SELECT again.

---

# Materialized View

## Definition

A **Materialized View** stores the **result of a query physically**.

Unlike a normal view, PostgreSQL **does not execute the query every time**.

Instead, it reads the stored data.

To get fresh data, you must refresh it.

---

## Syntax

```sql
CREATE MATERIALIZED VIEW view_name AS
SELECT ...
FROM ...
WHERE ...;
```

---

## Example

```sql
CREATE MATERIALIZED VIEW it_employees_mv AS

SELECT
    id,
    name,
    salary
FROM employees
WHERE department='IT';
```

Retrieve

```sql
SELECT * FROM it_employees_mv;
```

Output

| id  | name  | salary |
| --- | ----- | ------ |
| 1   | John  | 60000  |
| 3   | Bob   | 70000  |
| 4   | David | 80000  |

---

Now insert

```sql
INSERT INTO employees
VALUES
(5,'Emma','IT',90000);
```

Check the materialized view

```sql
SELECT * FROM it_employees_mv;
```

Output

| id  | name  | salary |
| --- | ----- | ------ |
| 1   | John  | 60000  |
| 3   | Bob   | 70000  |
| 4   | David | 80000  |

Emma is **not** there.

Because the materialized view hasn't been refreshed.

---

Refresh

```sql
REFRESH MATERIALIZED VIEW it_employees_mv;
```

Now

```sql
SELECT * FROM it_employees_mv;
```

Output

| id  | name  | salary |
| --- | ----- | ------ |
| 1   | John  | 60000  |
| 3   | Bob   | 70000  |
| 4   | David | 80000  |
| 5   | Emma  | 90000  |

---

# Dropping Objects

### Drop Table

```sql
DROP TABLE employees;
```

---

### Drop View

```sql
DROP VIEW it_employees;
```

---

### Drop Materialized View

```sql
DROP MATERIALIZED VIEW it_employees_mv;
```

---

# Alter View

You can rename a view.

```sql
ALTER VIEW it_employees
RENAME TO it_staff;
```

> If you need to change the query definition, use `CREATE OR REPLACE VIEW`.

```sql
CREATE OR REPLACE VIEW it_employees AS
SELECT id, name
FROM employees
WHERE department = 'IT';
```

---

# Alter Materialized View

Rename

```sql
ALTER MATERIALIZED VIEW it_employees_mv
RENAME TO it_staff_mv;
```

Change storage-related properties (owner, schema, tablespace, etc.) using `ALTER MATERIALIZED VIEW`, but **to change the query itself**, PostgreSQL does **not** support `CREATE OR REPLACE MATERIALIZED VIEW`.

The common approach is:

```sql
DROP MATERIALIZED VIEW it_employees_mv;

CREATE MATERIALIZED VIEW it_employees_mv AS
SELECT ...
```

# Comparison

| Feature                              | Table         | View                          | Materialized View                       |
| ------------------------------------ | ------------- | ----------------------------- | --------------------------------------- |
| Stores data physically               | ✅ Yes        | ❌ No                         | ✅ Yes                                  |
| Stores SQL query                     | ❌ No         | ✅ Yes                        | ✅ Yes                                  |
| Automatically reflects table changes | ❌ No         | ✅ Yes                        | ❌ No                                   |
| Needs refresh                        | ❌ No         | ❌ No                         | ✅ Yes                                  |
| Can INSERT/UPDATE/DELETE             | ✅ Yes        | Usually only simple views     | ❌ Not directly                         |
| Used for                             | Business data | Simplifying queries, security | Reporting, analytics, expensive queries |

---

# When to Use Each

### Use a Table when:

- You are storing application or business data.
- Users or applications need to insert, update, or delete rows.

### Use a View when:

- You want to simplify complex SQL.
- You need reusable queries.
- You want to expose only specific columns or rows.
- You always need the latest data.

### Use a Materialized View when:

- The query is expensive (joins, aggregations, millions of rows).
- Fast read performance is important.
- Slightly stale data is acceptable.
- You can refresh the results periodically (hourly, nightly, or on demand).
